# Этап 0 — пробник кабинетов: отчёт

Ветка `claude/stage-0`. Сделано строго в рамках SPEC §11 «Этап 0»; этапы 1–3 не начинались.

## Что сделано

**Бинарь `cmd/mp-reviews-probe`** (Linux и Windows), инструкция и чек-лист для пользователя —
`cmd/mp-reviews-probe/README.md`.

- Запускает **видимый** установленный Chrome с постоянным профилем кабинета: `-profile wb-ms` →
  `%LOCALAPPDATA%\mp-reviews\chrome-profiles\wb-ms` (на Linux — `~/.cache/mp-reviews/chrome-profiles/…`).
  Каталог считает `internal/chrome.ProfileDir` — агент этапа 3 должен использовать эту же функцию,
  тогда вход в кабинет общий. Имя профиля проверяется (`[a-z0-9][a-z0-9_-]{0,63}`), выйти из каталога
  профилей нельзя.
- Chrome через CDP: `--remote-debugging-port=0` (порт только на 127.0.0.1), адрес websocket берётся
  из `DevToolsActivePort`. Если Chrome с этим профилем уже открыт — понятная ошибка вместо
  «тихого» подключения к чужому процессу.
- **Ничего не делает в кабинете сам.** Единственные действия пробника: открыть адрес из `-url` при
  старте (необязательно) и закрыть Chrome при выходе.
- Записывает:
  - сетевые запросы страниц типов XHR, Fetch, Document (навигации) и EventSource: метод, адрес,
    заголовки (и те, что браузер отправил фактически, с Cookie — из `*ExtraInfo`), тело запроса,
    статус, заголовки и тело ответа, перенаправления, ошибки загрузки, длительность;
  - переходы (`frameNavigated` и переходы внутри SPA — `navigatedWithinDocument`), новые вкладки
    (с `opener_id`), iframe и воркеры — через `Target.setAutoAttach` с `waitForDebuggerOnStart`,
    поэтому **первый запрос новой вкладки не теряется** (проверено тестом);
  - журнал действий пользователя: клик, начало ввода, изменение поля, отправка формы — описание
    элемента (тег, id, name, role, aria-label, видимый текст до 80 символов, data-testid),
    без значений полей.
- В консоли: название шага + Enter → `marks/NN-<шаг>.html` (снимок DOM) и `.png` (скриншот текущей
  вкладки); `q` — завершить; также завершение по закрытию Chrome и по Ctrl+C.
- Вычистка секретов (`internal/probe/redact.go`): значения `Cookie` (имена cookie сохраняются),
  `Set-Cookie` (имя и атрибуты сохраняются), `Authorization` и любых заголовков, параметров адреса
  (query и фрагмент), полей форм, полей multipart и ключей JSON, в имени которых есть
  `token|auth|session|secret|sign` → `<скрыто>`, имена сохраняются.
- Выход — один zip `probe-<профиль>-<дата-время>.zip`: `events.jsonl` (все события по времени,
  сквозной `seq`), `marks/NN-<шаг>.html|.png`, `summary.md` (таблица: метод, хост + путь-шаблон,
  число, статусы, ключи верхнего уровня запроса и ответа, номера действий; хронология: какой запрос
  последовал за каким действием и отметкой шага).
- `internal/cdp` — свой минимальный клиент CDP и websocket (RFC 6455): маскирование, фрагменты,
  ping/pong, close, 64-битные длины, неограниченная очередь событий (обработчик может вызывать
  команды без взаимной блокировки).
- `Makefile` (`test`, `test-integration`, `lint`, `vuln`, `build`, `build-windows`, `check`),
  `.env.example`, `README.md`, `.gitignore` (результаты пробника в git не попадают).

**Зависимостей нет** — только стандартная библиотека (`go list -m all` → один модуль). В PR
обосновывать нечего.

### Приёмка этапа 0 (SPEC §11) — как проверено

`internal/probe/probe_chrome_test.go`, запускается в `make test`:

- `TestProbeRecordsLocalPageInHeadlessChromium` — настоящий headless Chromium (в среде уже был:
  `/opt/pw-browsers/chromium-1194`, Chromium 141) открывает локальную `httptest`-страницу с формой
  и кнопкой; отправка формы уходит `fetch` POST на `/api/complaint?token=…` с `Authorization: Bearer …`,
  `X-Session-Id`, cookie `sid`, в ответе `Set-Cookie` и `access_token`. «Пользователь» — отдельное
  CDP-подключение, которое кликает мышью (`Input.dispatchMouseEvent`) и печатает текст; пробник о нём
  не знает. Проверяется:
  - запрос записан с методом, типом Fetch, телом (`reason: 11`, текст), ответ — со статусом 200 и телом;
  - запрос **связан с действием**: в `summary.md` он стоит под действием «отправка формы», которое
    следует за кликом по «Пожаловаться»; клик записан ровно один раз; записан выбор основания
    («Отзыв не относится к товару»);
  - **ни одна** из 7 секретных строк (cookie, Set-Cookie, `?token=`, Authorization, X-Session-Id,
    `access_token` в ответе, `csrfToken` в теле) не встречается ни в одном файле zip; Cookie записан
    как `sid=<скрыто>`, адрес — `token=<скрыто>&page=1`;
  - zip содержит `events.jsonl`, `summary.md`, `marks/01-posle-zhaloby.html` (с кнопкой) и `.png`
    (валидный PNG), рабочий каталог после сборки удалён.
- `TestProbeRecordsNewTabFromFirstRequest` — клик открывает новую вкладку, её навигация и первый
  `fetch` записаны с `target_id` новой вкладки и телом ответа.
- Юнит-тесты: вычистка (заголовки, URL, JSON с сохранением порядка ключей, формы, multipart, текст/HTML,
  JWT), путь-шаблоны, ключи, связывание запросов с действиями и отметками, рендер `summary.md`,
  websocket-клиент на поддельном сервере, профили, `DevToolsActivePort`, непересечение имён записей.
- Бинарь проверен и вручную сквозным прогоном под Linux (Chromium через обёртку с `--headless=new`,
  т.к. дисплея нет): отметка шага, `q`, zip с `summary.md` и снимками.
- Стабильность: тесты Chromium прогнаны `-race -count=25` — без сбоев; тесты CDP — `-count=200`.

## Чего НЕ сделано и почему

- **`govulncheck ./...` не выполнен.** Хост `vuln.go.dev` запрещён политикой исходящего трафика этой
  среды (прокси отвечает 403 на CONNECT). Обходить ограничение не стал. Поэтому критерий «govulncheck
  без находок» **не подтверждён**. Смягчающее: у модуля нет ни одной зависимости, проверять остаётся
  только стандартную библиотеку go1.26.6. Нужно прогнать `govulncheck ./...` у себя или разрешить
  `vuln.go.dev` в настройках сетевой политики окружения.
- **Пробник не проверен на Windows и с настоящим видимым Chrome** — только сборка под Windows и работа
  с headless Chromium 141 под Linux. Пути Windows (`%LOCALAPPDATA%`, `%ProgramFiles%\Google\Chrome\…`),
  ввод кириллицы в консоли Windows и поведение видимого Chrome — проверить человеку (см. ниже).
- `make test-integration` — заглушка с сообщением: на этапе 0 БД нет (уточнение задания), тесты с
  PostgreSQL — с этапа 1.
- Не записываются: трафик WebSocket, скрипты/стили/картинки/шрифты (не XHR/fetch и не навигация — по
  SPEC не нужны), содержимое shadow DOM и iframe в снимке DOM (снимок — главного документа вкладки).
- Изображение, приложенное к жалобе, в запись не попадает: в multipart содержимое файла заменяется на
  `<файл: N байт>` (структура формы остаётся).

## Решения на развилках (SPEC не решает — выбран консервативный вариант)

1. **Список «секретных» имён расширен** сверх SPEC (`token, auth, session, secret, sign`):
   `cookie, csrf, xsrf, passw, jwt, api-key` и точные `sid, ssid, pwd`, а также заголовок WB
   `wb-seller-lk` (по `legacy/wb_reviews_poc/cabinet.py` он входит в сессию кабинета, но под правило
   SPEC не попадает). `authorizev3` из legacy покрывается `auth`. Плюс JWT (`eyJ….….…`) и
   `Bearer/Basic …` скрываются в любом месте. Цена — лишние скрытия (например, поле `author`,
   слово `design`): структура при этом сохраняется.
2. **Секреты вычищаются и в телах**, хотя SPEC говорит «тела сохраняются»: в JSON скрываются только
   значения ключей с секретными именами (порядок ключей и остальные значения — как были), в формах —
   значения таких полей, в прочем тексте (HTML, JS) — эвристика `имя=значение` / `"имя": "значение"`.
   Причина: записи потом могут лечь в `fixtures/probe/` (§11, этап 3), а токены в git недопустимы
   (CLAUDE.md). Идентификаторы кабинета вроде `x-supplier-id` **не** скрываются — они нужны для
   пункта 5 чек-листа (как понять, какой кабинет открыт); в Cookie скрываются все значения, имена видны.
3. **Значения полей ввода в журнал действий не пишутся** — только длина (для паролей и секретных полей
   — ничего). Введённый текст жалобы/ответа всё равно виден в теле запроса. Записывается текст
   выбранного пункта `<select>` (основание жалобы) и состояние флажков.
4. **Снимок DOM**: содержимое `<script>` удаляется, скрываются секретные атрибуты, значения скрытых и
   парольных полей, `<meta>` с csrf/token, секретные параметры в `href/src/action`; в `<head>`
   добавляется CSP `default-src 'none'`, чтобы открытый снимок не ходил в сеть с вашими cookie.
   Скриншоты не вычищаются (невозможно).
5. **Скрипты пробника работают в изолированном мире** (как расширение): странице не видны ни
   обработчики, ни функция-привязка. Но для доставки событий привязки пришлось включить
   `Runtime.enable` (без него Chromium 141 не присылает `Runtime.bindingCalled` — проверено). Это
   стандартный шаг Puppeteer/Playwright, но некоторые антиботы его замечают — см. «проверить человеку».
6. **Флагов `-headless` у бинаря нет**: SPEC требует видимый Chrome; headless — только опция пакета
   для тестов. В тестах под Linux добавляется `--no-sandbox` (контейнер работает от root).
7. **Имена файлов в zip — только ASCII**: название шага транслитерируется (`01-posle-zhaloby.png`),
   исходное название сохраняется в `events.jsonl` и `summary.md`. Так архив одинаково открывается
   любым распаковщиком Windows. Существующие записи не перезаписываются: при совпадении имени
   добавляется `-2`, `-3`, ….
8. **Связь запроса с действием**: запрос относится к последнему действию, если начался не позже 10 с
   после него (по времени страницы и `wallTime` запроса, а не по порядку прихода событий — порядок
   между процессами Chrome не гарантирован). Остальные запросы в хронологии помечены «запрос» без
   действия (фоновые опросы).
9. **Тела ограничены 1 МиБ** каждое (`body_truncated`, `body_size` — исходный размер); бинарные
   ответы (картинки и т.п.) не сохраняются, только размер (`body_binary_omitted`).
10. Воркеры расширений Chrome (`chrome-extension://`) не записываются.
11. При сбое подписки на события пробник не продолжает «вслепую»: сохраняет частичную запись и выходит
    с ошибкой. Запись пишется построчно на диск сразу — при аварийном завершении данные остаются в
    рабочем каталоге `probe-<профиль>-<время>/`.
12. Chrome закрывается при выходе штатно (`Browser.close`), чтобы профиль и вход в кабинет сохранились.

## Что проверить человеку на живом кабинете

1. **Windows**: запуск `mp-reviews-probe.exe -profile wb-ms -url https://seller.wildberries.ru/` —
   Chrome находится сам, окно видимое, профиль создаётся в `%LOCALAPPDATA%\mp-reviews\chrome-profiles\wb-ms`,
   после повторного запуска вход в кабинет сохранён. Названия шагов по-русски вводятся в консоли
   нормально (в `summary.md` — без кракозябр).
2. **Антибот**: не появляются ли 403/498/капча чаще, чем обычно, когда работает пробник (из-за
   `Runtime.enable`, решение 5). Если да — это важно и для агента этапа 3, сообщите.
3. **Вычистка на реальных данных**: пролистать `summary.md` и поискать в `events.jsonl` куски своих
   токенов (для WB — например, первые 8 символов значения заголовка `authorizev3` или `wb-seller-lk`
   из DevTools браузера; для Ozon — значения заголовков запросов кабинета, похожие на ключи сессии).
   Значения cookie скрываются всегда, риск — в собственных заголовках и полях площадки с именами,
   не попадающими в правила. Если что-то нашлось — дополнить `secretWords` в `internal/probe/redact.go`.
4. **Полнота**: при подаче жалобы и ответе в `summary.md` под соответствующими действиями видны
   запросы подачи и их ответы (с телом). Если кабинет открывает диалоги в iframe или новой вкладке —
   их запросы тоже есть (`target_id` другой вкладки/iframe).
5. **Снимки** `marks/*.html` открываются и по ним видны кнопки/диалог; скриншоты — той вкладки, где
   вы работали (если вкладок несколько, берётся вкладка последнего действия или перехода).
6. Размер zip после типичной сессии (тела ограничены 1 МиБ на запрос; если кабинет отдаёт большие
   HTML — архив может быть десятки МБ).
7. Прогнать `govulncheck ./...` (здесь не удалось, см. выше).
