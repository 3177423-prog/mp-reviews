# Правила работы в этом репозитории

Что строим — в `SPEC.md`. Прочитать целиком до начала работы. Работать **только над текущим этапом**
(§11 SPEC), который назван в задании сессии; не заходить в следующие этапы и не добавлять функций,
которых нет в SPEC.

Проект потом встраивается в `mp-collector`, поэтому его соглашения обязательны.

## Стек

- Go **1.26** (`go 1.26.0`, `toolchain go1.26.6`), модуль — `github.com/<owner>/mp-reviews`.
- PostgreSQL **18**, драйвер `github.com/jackc/pgx/v5`, миграции — `github.com/pressly/goose/v3`,
  встроенные в бинарь (`embed`), нумерованные: `00001_*.sql`, `00002_*.sql`, …
- Метрики — `github.com/prometheus/client_golang`, логи — `log/slog`.
- Предпочитать стандартную библиотеку новым зависимостям. Каждую новую зависимость обосновать в PR.
- Раскладка: `cmd/<бинарь>/` — точки входа; `internal/...` — код. Отдельные бинари: сервис,
  `cmd/migrate`, утилиты (импорт шаблонов, офлайн-оценка).

## База данных

- Схему меняют **только нумерованные goose-миграции**. Сервис при старте миграции **не** запускает —
  для этого `cmd/migrate`.
- Не использовать `serial` / `bigserial`. Малые справочники — `generated always as identity`;
  крупные сущности без стабильного ключа маркетплейса — UUIDv7; факты — натуральные ключи маркетплейса.
- **Каждая** таблица, view и **каждая колонка** получают `COMMENT ON` в той же миграции.
- `DO $$ … $$` и функции оборачивать в `-- +goose StatementBegin` / `-- +goose StatementEnd`.
- `raw jsonb` — nullable, пустой payload не писать как `'{}'`; хранить не дольше 2 месяцев.
- Работа с БД — **батчами**. Справочники, нужные при массовой обработке, прогревать в память до цикла;
  не резолвить их построчными запросами.
- Собственные таблицы — в своей схеме. Таблицы `mp-collector` (`public.sellers`, `public.marketplaces`,
  `public.marketplace_tokens`, `wb.products`, `oz.products`) — внешние: основные миграции их **не**
  создают; для тестов — отдельный набор тестовых миграций-заглушек (SPEC §10.1).

## Внешние API

- Назначение методов, параметры и лимиты — по **официальной текстовой документации** маркетплейса.
  Swagger-схемам WB не доверять как источнику полей и обязательности — они расходятся с фактическим API.
  Поля ответа делать терпимыми к отсутствию.
- Ретраи: **401/403 — сразу стоп; 400 — без повтора** (это ошибка запроса или сменившийся контракт);
  всё остальное — ограниченное число повторов с backoff и `Retry-After`, через общий лимитер.
- В тестах **никаких живых вызовов**: WB, Ozon, кабинет и ИИ-провайдеры — только через `httptest`-серверы
  и поддельные реализации. Реальных ключей в среде нет и не будет.

## Секреты

В коде, тестах, фикстурах и истории git не должно быть токенов, паролей, cookie, адресов таблиц,
chat_id. Конфигурация — только через переменные окружения; все ключи перечислить в `.env.example`
без значений.

## Качество

Обязательные цели `Makefile`:

- `make test` — юнит-тесты (`go test ./... -race`);
- `make test-integration` — берёт PostgreSQL из `TEST_DATABASE_URL`, создаёт временную БД, применяет
  основные и тестовые миграции, гоняет интеграционные тесты, удаляет БД. Если PostgreSQL в среде нет —
  поставить (`apt-get install postgresql`) и описать это в README;
- `make lint` — `golangci-lint` v2 с конфигом `.golangci.yml` (он скопирован из `mp-collector`, не ослаблять);
- `govulncheck ./...` без находок.

Этап считается сделанным, только когда всё это проходит **и** выполнены критерии приёмки этапа из SPEC.
Не выдавать непроверенное за сделанное.

## Как вести работу

- `legacy/` — справочник по поведению и граблям. Код оттуда не копировать как есть: переносить логику
  и тесты на неё, исправляя перечисленные в SPEC баги.
- На развилке, которую SPEC не решает, выбирать **более консервативный** вариант (не отправлять, не
  перезаписывать, в ручную очередь) и записывать решение в описание PR.
- Описание PR: что сделано; чего **не** сделано и почему; принятые решения на развилках; как проверено
  (команды и их результат); что нужно проверить человеку на реальных данных.
- Комментарии и документация — на русском. Имена в коде — на английском.
