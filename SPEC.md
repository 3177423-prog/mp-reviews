# mp-reviews — автоответчик и жалобы на отзывы Wildberries и Ozon

Рабочее название. Проект пишется как самостоятельный, но **потом встраивается в `mp-collector`**
(Go-сервис сбора данных маркетплейсов, PostgreSQL). Поэтому соглашения `mp-collector` — обязательны
(см. `CLAUDE.md`), а всё, что принадлежит `mp-collector`, здесь — внешняя зависимость за интерфейсом.

В `legacy/` лежат два работающих сейчас проекта — это **справочник по поведению и граблям**, а не код
для копирования:

- `legacy/auto_answer/` — нынешний автоответчик (Go + PostgreSQL), отвечает по шаблонам.
- `legacy/wb_reviews_poc/` — система жалоб на отзывы WB (Python + SQLite), подала ~10 000 жалоб.
  Её выводы — в `legacy/wb_reviews_poc/LEGACY_NOTES.md`; запросы к кабинету WB — в `cabinet.py`.

`fixtures/google_response.json` — пример реальных шаблонов ответа (артикулы заменены). **Только как
тестовые данные.** Google-таблицы проектом не используются никак; перенос существующих шаблонов в БД
делается отдельным внешним скриптом и в задачу не входит.

---

## 1. Цель

Для каждого нового отзыва на WB и Ozon система решает, **ответить на него или пожаловаться**, готовит
текст и выполняет действие сама, когда уверена. Когда не уверена — кладёт отзыв в ручную очередь
**с обоими готовыми текстами** (ответ и жалоба), и человек одним нажатием выбирает.

Менеджеры настраивают шаблоны, рекомендации и пороги **через портал** (отдельная страница
со своими доступами). Портал — отдельный проект; здесь нужен только HTTP API для него.

## 2. Состав системы

1. **Сервер** (Linux, Go) — сбор отзывов через API, ИИ-решения, тексты, отправка ответов через API,
   очередь заданий для браузерного агента, ручная очередь, admin API.
2. **Браузерный агент** (отдельный бинарь под **Windows**, Go) — выполняет в кабинетах маркетплейсов
   то, чего нет в API: **подаёт жалобы на WB и Ozon** и **отвечает на отзывы Ozon** для кабинетов без
   доступа к API отзывов. Работает через Chrome на компьютере пользователя, **cookies и сессии никогда не
   покидают этот компьютер и нигде на сервере не хранятся** (§8).

**Не делаем:** веб-интерфейс портала; вопросы покупателей; перенос данных старых систем, кроме истории
отзывов (§10.7); деплой.

## 3. Как работает старая система (что сохраняем и что чиним)

Проверено по коду `legacy/auto_answer/`:

- Раз в 10 минут по каждому продавцу: отзывы **только за последние 7 дней** (в новой системе — 30 дней, §4) (WB: неотвеченные + отвеченные-непросмотренные;
  Ozon: необработанные).
- На 1–3★ отвечает **только на пустые** отзывы; 1–3★ с текстом остаются без ответа.
- На 4–5★ проверяет стоп-фразы; при совпадении не отвечает и отдаёт менеджеру.
- Ответ — случайная склейка блоков: приветствие + благодарность + мотивация + основной текст +
  рекомендация (P.S.) + прощание, отдельные наборы для 1–3★ и 4–5★, отдельные рекомендации для WB и Ozon.
  Подстановки: `{{name}}` (имя покупателя), `{{productName}}` (название товара **в винительном падеже**),
  `{{recomendation}}`. Если имени нет — убираются `", {{name}}"` и `"{{name}},"`.
- **Рекомендации сейчас на практике используются только общие** (блоки «рекомендации WB/Ozon»);
  механизм рекомендаций по конкретному товару в коде есть, но не востребован.
- Стоп-фразы (**в новой системе не используются** — их заменило чтение отзыва ИИ и флаги риска, §5.1): слово или фраза из нескольких слов подряд; `*` в начале/конце слова = совпадение по
  суффиксу/префиксу, с обеих сторон = по подстроке.

**Баги, которые не переносить:**

- генератор случайных чисел инициализируется текущей секундой на каждый вызов → отзывы,
  обработанные в одну секунду, получают одинаковый ответ;
- пустой список блоков → `rand.Intn(0)` → паника → обработка всего продавца обрывается;
- regexp компилируется на каждый отзыв;
- «отвеченные-непросмотренные» отзывы WB обрабатываются повторно — **существующие ответы не
  перезаписывать никогда**, только по явному действию человека;
- соответствие продавец → набор шаблонов задано индексом массива.

## 4. Конвейер обработки отзыва

```
сбор → предфильтр → ИИ-решение → политика → тексты → проверка → действие → отслеживание исхода
```

1. **Сбор.** Опрос API раз в N минут (по умолчанию 10) по каждой паре продавец × маркетплейс с
   действующим ключом. Обрабатываются отзывы **не старше 30 дней** — дальше смысла нет. Upsert по
   натуральному ключу маркетплейса. Обновлять и состояние уже известных отзывов: есть ли ответ,
   подана ли жалоба.
2. **Предфильтр (детерминированно, без ИИ):**
   - уже есть ответ → не отвечаем;
   - жалоба уже подана — по данным API (на WB `isAbleSupplierFeedbackValuation = false` или заполнен
     `supplierFeedbackValuation`) или по нашей истории → жалобу не подаём. **Главная защита от двойной
     жалобы**, в том числе на отзывы, по которым жаловалась старая система;
   - по отзыву уже была **отклонённая жалоба** → повторно автоматически не жалуемся никогда (§7.5);
   - отзыв старше срока подачи жалобы → жалоба невозможна;
   - пустой отзыв (нет текста, плюсов, минусов) → ответ по шаблону без ИИ; **жалоба на пустой отзыв
     не подаётся никогда** (такие жалобы одобрялись лишь в ~14% случаев, решение заказчика).
3. **ИИ-решение** — для **каждого** отзыва с текстом, при любой оценке: и на 5★ бывает негатив, по
   которому нужна жалоба без ответа. Результат — строгий JSON (§5).
4. **Политика** — детерминированный код поверх решения ИИ, пороги по продавцу (§5.2). Однозначный случай
   — автоматически, сомнительный — человеку.
5. **Тексты.** Готовятся все нужные для выбранного действия, а для ручной очереди — **оба**.
6. **Проверка текстов** (§6.4, §7.4). Не прошёл проверку → ручная очередь, не отправка.
7. **Действие.** Ответ через API — сервером; жалоба и ответ через кабинет — заданием браузерному агенту.
   Перед действием **повторно** проверить актуальное состояние отзыва. Запись о намерении делается до
   действия; уникальность «одно действие данного типа на отзыв» — на уровне БД.
8. **Исход жалобы** отслеживается (§7.5).

**Ответ и жалоба взаимоисключающие в автоматическом режиме:** на отзыв, на который жалуемся, не отвечаем.

## 5. ИИ-решение и политика

### 5.1. Что возвращает модель

Строгий JSON: `action` (`answer` | `complaint` | `manual`), `confidence` (0..1), для жалобы — `basis`
(строго из списка оснований площадки, §7.2), `strength` (`strong` | `weak` | `none`), краткое обоснование,
признаки (негатив при высокой оценке, вопрос покупателя, брак, некомплект, доставка, …) и **флаги риска**
(`risk_flags`): угроза суда или обращения в госорганы (Роспотребнадзор, прокуратура и т.п.), вред здоровью
или угроза безопасности, подозрение на подделку или мошенничество, персональные данные в тексте. Список
флагов — настройка. На вход — маркетплейс, оценка, текст, плюсы, минусы, теги покупателя, число фото/видео,
короткое название товара.

Флаги риска заменяют прежние стоп-слова: отдельного словаря и поиска по нему нет, опасные темы распознаёт
модель, а политика гарантирует, что такие отзывы увидит человек.

Модель **не придумывает нарушение**: «основания нет» — нормальный исход, он ведёт к ответу.
Промпт версионируется, версия сохраняется с каждым решением.

### 5.2. Политика по умолчанию (всё настраивается по продавцу)

| решение ИИ | действие |
|---|---|
| есть любой флаг риска | **всегда** ручная очередь с двумя готовыми текстами, при любой уверенности |
| `complaint`, `strength = strong`, `confidence ≥ T_complaint` | авто-жалоба |
| `answer`, `confidence ≥ T_answer` | авто-ответ |
| всё остальное | ручная очередь с двумя готовыми текстами |

**Режим запуска по умолчанию — «только черновики»** для каждого продавца: всё считается и сохраняется,
ничего не отправляется, пока режим не переключён явно. Отдельно включаются авто-ответы и авто-жалобы.

### 5.3. Данные, на которые опираться (старая система жалоб WB, ~10 000 решённых жалоб)

- Одобряемость в среднем **~43%**, WB решает в среднем за ~7 часов, максимум за сутки.
- Пустые отзывы одобряют плохо (**~14%**); с тегом покупателя «плохое качество» — ~20%;
  «Другое» как основание — ~33%; «Отзыв не относится к товару» — ~65–70%.
- Некомплект/недостача как «Отзыв не относится к товару» (ключ 11) одобрялись в 70% против 52% под
  «Другое» — эту маршрутизацию делать **кодом**, а не надеяться на модель.
- Текст жалобы почти не влияет на исход (40–45%), кроме **ссылки на карточку** (~62%).
- **Оценка силы работает только у сильной модели.** Sonnet раскладывал жалобы на сильные/слабые/без
  основания примерно поровну, и метка предсказывала исход (69% / 49% / 30% одобрений). DeepSeek
  отправил 88% в «слабое» — по его метке фильтровать было нельзя. Поэтому пороги **не угадывать**:
  офлайн-оценка (§10.3), пороги выставляются по ней.

## 6. Ответы

### 6.1. Шаблоны в БД

По продавцу:

- блоки ответа по группам оценок (1–3★ и 4–5★): приветствия, благодарности, мотивации, основные тексты,
  общие рекомендации WB, общие рекомендации Ozon, прощания;
- рекомендации по конкретному товару: для SKU — текст рекомендации (необязательны).

### 6.2. Рекомендации: общие или по товару

Настройка продавца: **общие** (по умолчанию, как сейчас) или **по товару**. В режиме «по товару» для
товара с персональной рекомендацией берётся она, для остальных — общая. Отсутствие персональной
рекомендации — штатная ситуация: никаких ошибок, отчётов и уведомлений по ней нет.

### 6.3. Сборка ответа

По умолчанию — шаблон: случайный вариант каждого блока, подстановки, корректная работа при пустом наборе
(блок пропускается, ошибка в отчёт — без паники). Один генератор случайных чисел на процесс.

Для отзывов, где шаблон не подходит (конкретная претензия, вопрос, смешанный отзыв), ответ генерирует
модель, используя блоки шаблона продавца как образец тона и подпись. Модель для генерации ответа
настраивается отдельно — можно подключить более сильную, чем для классификации.

### 6.4. Проверка ответа перед отправкой

Длина в пределах лимита площадки (уточнить по официальной документации); нет неподставленных `{{…}}`;
нет обещаний возврата, компенсаций и скидок, которых нет в шаблонах; нет ссылок на сторонние сайты.
Не прошла → ручная очередь.

### 6.5. Короткие названия товаров

Для `{{productName}}` нужна **короткая** форма: **от 1 до 5–7 слов**, в винительном падеже
(«Отлично, что вы выбрали *энзимную пудру*»), 2–3 варианта на товар. Товар появился в каталоге или
изменилось его название → модель генерирует варианты, статус «сгенерировано». Длиннее 7 слов или не
прошло проверку падежа моделью → не сохраняется, товар — в отчёт. Правка человеком ставит статус
«проверено», такие варианты автоматически **не перезаписываются**.

### 6.6. Каналы отправки ответа

- **WB** — через API отзывов.
- **Ozon** — настройка кабинета: через API (для кабинетов с подпиской, дающей доступ к API отзывов)
  или через браузерного агента (для остальных).

## 7. Жалобы

Подаются **только браузерным агентом через кабинет**, одинаково для WB и Ozon. Логика подготовки
переносится из `legacy/wb_reviews_poc/` (`analyzer.py`, `cabinet.py`, `autosubmit.py`).

### 7.1. Проверенные факты по WB

- `GET feedbacks-api.wildberries.ru/api/v1/feedbacks` — **фильтра по оценке нет**, фильтровать у себя
  по `productValuation`. Лимит ~3 запроса/с, `take ≤ 5000`, `skip ≤ 199990`.
- **Подать жалобу через официальный API нельзя** — только через кабинет.
- Признак поданной жалобы в отзыве: `isAbleSupplierFeedbackValuation = false` и
  `supplierFeedbackValuation = <ключ причины>`; ключ **11 = «Отзыв не относится к товару»**.
  Исход (одобрена/отклонена) в официальном API не виден — только в кабинете.

### 7.2. Кабинет WB

- На отзыв можно пожаловаться **один раз**. Текст ≤ 1000 символов, одно изображение ≤ 3600 КБ,
  срок — 30 дней. Статусы: в очереди, на рассмотрении, одобрена (отзыв скрыт), отклонена, пересмотрена.
- Основания — **ровно** из формы кабинета: «Отзыв оставили конкуренты», «Отзыв не относится к товару»,
  «Спам-реклама в тексте», «Нецензурная лексика», «Отзыв с политическим контекстом»,
  «Угрозы, оскорбления», «Другое». Своих не выдумывать.
- Переключение кабинета подменой cookie ненадёжно: WB **молча отдаёт прежний кабинет**, если сменить
  не ту cookie (в legacy — `x-supplier-id` вместо `x-supplier-id-external`); в `mp-collector` подмена
  cookie для Ozon давала 403. Поэтому у агента **один профиль браузера на кабинет** (§8), а перед
  каждым действием — проверка, что открыт именно ожидаемый кабинет. Не подтвердилось — **не подавать**.

### 7.3. Кабинет Ozon

Основания, лимиты и **запросы** кабинета Ozon для жалоб и ответов **неизвестны** — их снимает пробник
этапа 0 на реальном кабинете. В этом проекте: общий механизм агента, интерфейс адаптера площадки и
адаптер-заглушка для Ozon с тестами на поддельном кабинете. Реальный адаптер Ozon — по записям пробника.

Для WB запросы кабинета (подача жалобы, статусы) известны по legacy (`cabinet.py`); по ним пишется адаптер,
а записи пробника с живого кабинета — сверка актуальности.

### 7.4. Маршрутизация и проверка текста жалобы

- некомплект/недостача → «Отзыв не относится к товару»; слабые теги покупателя (например,
  «плохое качество») понижают силу — см. `route()`, `MISROUTED`, `WEAK_TAGS` в `legacy/.../analyzer.py`;
- текст не длиннее лимита площадки; не подрывает сам себя (не признаёт вину продавца, не соглашается
  с претензией); не ссылается на фото, если их нет; не выдумывает фактов — см. `draft_is_sound` в legacy;
- по возможности включать ссылку на карточку товара — единственное, что заметно поднимало одобряемость.

### 7.5. Исход и защита от повторной жалобы

Агент собирает статусы поданных жалоб из кабинета, сервер их сохраняет. **Отклонённая жалоба ставит на
отзыв постоянную метку «жалоба отклонена»**: автоматическая жалоба на такой отзыв больше невозможна ни
при каких условиях (снять метку может только человек в ручной очереди). Сам отзыв возвращается в
конвейер на ответ, если ответить ещё можно.

## 8. Браузерный агент (Windows)

### 8.1. Как работает

Повторяет проверенный паттерн `mp-collector` (`cmd/mp-ozon-portal-refresh`, `cmd/mp-wb-storefront-refresh`):

- отдельный Go-бинарь, собирается под Windows (`GOOS=windows`), работает с установленным Chrome через
  **Chrome DevTools Protocol** (`--remote-debugging-port`, websocket), без тяжёлых сторонних библиотек;
- **несколько постоянных профилей Chrome — по одному на кабинет** (`--user-data-dir` в `%LOCALAPPDATA%`);
  вход в кабинет пользователь выполняет один раз вручную в каждом профиле;
- направление обратное клиентам `mp-collector`: агент **забирает задания из очереди сервера** и выполняет
  их в кабинете, а на сервер возвращает только результат;
- для каждого кабинета: запуск Chrome с его профилем → **проверка авторизации и того, что открыт
  ожидаемый кабинет** → выполнение заданий → отчёт на сервер → закрытие Chrome;
- браузер — **носитель сессии**, а не экран для кликов: задания выполняются **запросами кабинета изнутри
  открытой страницы** (fetch в контексте страницы через CDP), поэтому они уходят с cookies, заголовками и
  отпечатком настоящего браузера. Интерфейс не кликается. Результат подтверждать по ответу на запрос;
  не подтвердилось — исход неизвестен (§8.4);
- **ответ 403 или 498** (антибот площадки) → закрыть этот Chrome, запустить новый с тем же профилем,
  снова проверить авторизацию и кабинет и продолжить с того же задания. Это штатный путь, не авария.
  Перезапусков подряд без единого успешного запроса — ограниченное число (настройка); превышено →
  остановка по кабинету и уведомление;
- запросы каждой площадки (адрес, метод, тело, признак успеха) описаны в адаптере площадки, отдельно
  от общего механизма агента;
- **cookies, токены кабинета и полные ответы кабинета не передаются на сервер и не пишутся в логи и файлы**;
  на сервер уходят только результаты заданий и статусы жалоб;
- запуск — Планировщиком Windows с заданным интервалом; сбой одного кабинета не останавливает остальные.

### 8.2. Защита кабинета от блокировки

Умеренная скорость: лимит запросов **на каждый endpoint** и на кабинет (никаких сотен запросов в секунду
в один адрес), случайный разброс пауз, запросы в кабинете строго последовательно, работа только в
заданные часы. 403/498 — перезапуск браузера (§8.1). Выход из сессии (требование повторного входа),
капча, несовпадение кабинета, неожиданный ответ → **остановка по этому кабинету**, задания возвращаются в
очередь, уведомление. Лимиты задаются на сервере и приходят агенту вместе с заданиями.

### 8.3. Регистрация агента (решение заказчика)

1. В портале администратор создаёт одноразовый код привязки (живёт 10 минут) и указывает, какие
   кабинеты доступны этому компьютеру.
2. Агент при первом запуске вводит код; сервер выдаёт **токен устройства**: отдельный на компьютер,
   с правами только на задания своих кабинетов, отзываемый. На сервере хранится только хеш.
3. Агент хранит токен зашифрованным средствами Windows (DPAPI), не в открытом файле.
4. В портале видны зарегистрированные устройства, их кабинеты и время последнего выхода на связь;
   любое можно отключить.

### 8.4. Протокол сервер ↔ агент

HTTPS + JSON, описание в OpenAPI. Агент: получает задания своих кабинетов (с арендой на время выполнения,
чтобы два агента не взяли одно задание), отчитывается о результате каждого, отправляет статусы жалоб,
сообщает о себе (версия, кабинеты, последний успешный вход). Сервер повторно проверяет состояние отзыва
перед выдачей задания. Задание, не подтверждённое в срок аренды, возвращается в очередь — но только если
агент явно сообщил, что действие **не** выполнено; при неизвестном исходе — в ручную очередь, чтобы не
подать жалобу дважды.

## 9. Ручная очередь и admin API

**Ручная очередь.** Карточка: отзыв, товар, решение ИИ с обоснованием, флаги риска,
**готовый текст ответа и готовый текст жалобы**. Действия: отправить ответ, подать жалобу,
отредактировать любой текст и отправить, пропустить, снять метку «жалоба отклонена». Каждое действие —
с автором и временем в журнале.

**Admin API для портала** — JSON по HTTP + OpenAPI. Справочники (CRUD): блоки шаблонов, рекомендации,
короткие названия товаров (с перегенерацией), настройки продавца (пороги,
режимы, модели, режим рекомендаций, канал ответов Ozon). Ручная очередь. Устройства агента (коды
привязки, список, отключение, лимиты). Отчёты: ответы и жалобы, одобрено/отклонено, очередь, ошибки
(нет названий, ключ недействителен, агент давно не выходил на связь).

Авторизация — интерфейсом (middleware). В проекте — простая реализация на bearer-токенах с ролями
(чтение / правка справочников / решения по очереди / управление устройствами); при встраивании заменится
на систему `mp-collector`.

## 10. Технические требования

### 10.1. Внешние зависимости за интерфейсами

- **Продавцы и ключи API.** В `mp-collector` это `public.sellers`, `public.marketplaces` (поле `code`:
  `wb`, `oz`), `public.marketplace_tokens` (ключи **зашифрованы**, `data_tokens_enc bytea`). Здесь —
  интерфейс «дай действующие ключи продавца для маркетплейса». Продавец обрабатывается, **только если
  есть действующий ключ**; 401/403 → пара продавец × маркетплейс помечается неактивной, уведомление,
  остальные продолжают работать.
- **Каталог товаров** — `wb.products` (`nm_id`, `title`, `seller_id`, `imt_id`, `article`, …) и
  `oz.products` в `mp-collector`. Здесь — интерфейс «товары продавца и их названия».
- Для разработки и тестов — простые реализации этих интерфейсов и **отдельный набор тестовых миграций**
  с совместимыми заглушками внешних таблиц. Основные миграции создают только собственную схему.

```sql
-- mp-collector: 00001_initial_schema.sql (для совместимости заглушек)
create table public.sellers (id smallint generated always as identity primary key, title text not null,
  is_deleted boolean not null default false, created_at timestamp not null, updated_at timestamp not null,
  deleted_at timestamp);
create table public.marketplaces (id int generated always as identity primary key, code text not null,
  title text not null, title_en text, url_base text, url_seller text, url_doc text, url_image text);
create table public.marketplace_tokens (id bigint generated always as identity primary key,
  seller_id smallint not null references public.sellers(id),
  marketplace_id int not null references public.marketplaces(id), data_tokens_enc bytea not null,
  created_at timestamptz not null, updated_at timestamptz not null, unique (seller_id, marketplace_id));
```

### 10.2. ИИ-провайдеры

Интерфейс провайдера; реализации: OpenAI-совместимый Chat Completions (DeepSeek по умолчанию, подходит и
для других совместимых сервисов) и Anthropic Messages. Модель задаётся **отдельно для каждого шага**:
классификация, текст жалобы, генерация ответа, короткие названия. Настраиваемая
цепочка запасных провайдеров. Надёжный разбор JSON (ответ должен начинаться с `{`; обрезанный ответ —
повтор с бо́льшим лимитом токенов). С каждым решением сохранять провайдера, модель, версию промпта,
токены, время.

### 10.3. Офлайн-оценка

Команда, прогоняющая классификатор по размеченному CSV (текст, оценка, теги, фактическое решение или
исход жалобы) и печатающая долю авто-решений и точность при разных порогах. Пороги §5.2 выбираются по ней.
Реальный набор данных в репозиторий не попадает; в репозитории — маленький выдуманный пример.

### 10.4. Надёжность

- Внешние HTTP-вызовы (правило `mp-collector`): **401/403 — сразу стоп; 400 — без повтора, это ошибка
  запроса или сменившийся контракт, её обязательно разбирать; всё остальное — ограниченные повторы с
  backoff, `Retry-After` и общим лимитером.**
- Идемпотентность действий гарантирует БД, а не память процесса. Перезапуск посреди прогона не приводит
  к двойной отправке.
- Одна упавшая пара продавец × маркетплейс не останавливает остальные.

### 10.5. Наблюдаемость

Структурированные логи; метрики Prometheus (собрано, решения по типам, отправлено, ошибки, размер
очередей, задержка от появления отзыва до действия, стоимость ИИ, агенты на связи); уведомления через
интерфейс (реализация для Telegram — с поддержкой HTTP-прокси: с российских серверов Telegram API недоступен).

### 10.6. Конфигурация

Только переменные окружения, `.env.example` со всеми ключами без значений. Никаких секретов, токенов,
адресов и chat_id в коде.

### 10.7. Перенос отзывов из старой базы

Утилита `cmd/migrate-legacy-reviews`, запускается на сервере `mp-collector`. Делается по образцу уже
существующей там `cmd/migrate-legacy-product-analytics`:

- источник — переменные `LEGACY_PGHOST`, `LEGACY_PGPORT`, `LEGACY_PGUSER`, `LEGACY_PGPASSWORD`,
  `LEGACY_PGDATABASE`; приёмник — `DATABASE_URL`. Это **те же имена**, что уже заданы в окружении сервера
  `mp-collector`, — утилита должна запускаться без правки `.env`;
- по умолчанию — пробный прогон: читает, считает, сверяет, **ничего не пишет**; запись только с флагом
  `-apply`; `-batch-size` (по умолчанию 5000, допустимо 100–50000); работа пачками, без построчных запросов;
- источник только читается;
- идемпотентно: повторный запуск не создаёт дублей (upsert по натуральному ключу `wb_id` / `oz_id`);
  прерванный перенос можно просто запустить снова;
- таблицы источника (см. `legacy/auto_answer/models/`):
  `wb.feedbacks` (`seller_id, wb_id, feedback_text, advantages, defects, valuation, created_at, nm_id,
  imt_id, tech_size, user_name, matching_size, parent_id, article`) и
  `oz.feedbacks` (`seller_id, oz_id, feedback_text, valuation, created_at, product_id, sku, is_rating,
  is_delivered`). Сведений об ответах в них нет;
- **перенесённые отзывы — только история**: сам перенос не создаёт ни решений ИИ, ни черновиков, ни
  заданий. Действовать по отзыву конвейер может, только когда получил его заново через API (оттуда же
  приходит актуальное состояние: есть ли ответ, подана ли жалоба) и только в пределах окна 30 дней;
- итоговый отчёт: прочитано, добавлено, пропущено как уже существующие, отброшено с причиной
  (например, продавец не найден).

## 11. Этапы

Каждый этап — отдельная сессия и отдельный PR. Этап закрыт, когда проходят `make test`,
`make test-integration` (с этапа 1), `make lint`, `govulncheck`, сборка под Windows (для этапов 0 и 3),
и выполнены критерии приёмки.

### Этап 0. Пробник кабинетов

Нужен, чтобы снять с живых кабинетов WB и Ozon то, чего нельзя узнать из облака: **какие запросы
отправляет кабинет** для жалобы, ответа, статусов и проверки кабинета, с какими телами и какие ответы
получает. Пробник запускает пользователь у себя на Windows; по записям пишутся адаптеры площадок этапа 3.

**Бинарь `cmd/mp-reviews-probe`** (сборка под Windows и Linux), Chrome через CDP, как у агента (§8.1):

- запускает **видимый** Chrome с постоянным профилем кабинета: `-profile wb-ms` → каталог профиля в
  `%LOCALAPPDATA%` — **тот же, что будет у агента**, чтобы вход в кабинет делался один раз на оба;
- **ничего не делает сам** — только наблюдает. Все действия в кабинете пользователь выполняет руками;
- записывает: сетевые запросы страницы (XHR/fetch и навигации — метод, адрес, заголовки, тело запроса,
  статус, тело ответа), а также краткий журнал действий пользователя (клик, ввод, отправка формы) —
  только чтобы сопоставить, какой запрос каким действием вызван; переходы между страницами, новые вкладки
  и iframe (auto-attach);
- в консоли пользователь отмечает шаги: вводит название шага и Enter → пробник сохраняет снимок DOM и
  скриншот с этой меткой; `q` — завершить;
- **вычищает секреты**: значения `Cookie`, `Set-Cookie`, `Authorization` и любых заголовков и параметров
  запроса, в имени которых есть `token`, `auth`, `session`, `secret`, `sign`, заменяются на `<скрыто>`
  (имена сохраняются). Тела запросов и ответов сохраняются — по ним восстанавливается структура;
  файл результата остаётся у нас и **никуда не публикуется**;
- на выходе — один zip: `events.jsonl` (всё по времени), `marks/NN-<шаг>.html` и `.png`, `summary.md`
  (таблица запросов: метод, хост + путь-шаблон, число, статусы, ключи верхнего уровня запроса и ответа;
  какой запрос последовал за каким действием и отметкой шага).

**Чек-лист для пользователя** (в README пробника), отдельно для WB и Ozon: 1) открыть список отзывов и
найти конкретный отзыв; 2) пожаловаться на отзыв: кнопка, диалог, выбор основания, текст, при
возможности изображение, отправка; 3) где видны статусы жалоб; 4) ответить на отзыв (для Ozon
обязательно, для WB по желанию); 5) как определить, какой кабинет открыт (какой запрос и ответ это
показывают); 6) если встретятся — ответы 403/498, капча и повторный вход. Действия выполняются настоящие, поэтому для записи жалобы и
ответа брать отзывы, по которым их и так нужно сделать.

Приёмка: тестовая локальная HTML-страница с кнопкой и отправкой формы через fetch, открытая в headless
Chromium (поставить в среде), — пробник записывает запрос с ответом и связывает его с действием,
вычищает `Cookie`/`Authorization`/`?token=` из записи (проверяется тестом), собирает zip с `summary.md`;
бинарь собирается под Windows.

### Этап 1. Фундамент и ответы по шаблонам (без ИИ)

Схема и миграции; клиенты WB и Ozon для отзывов и ответов через API; сбор; справочники в БД; сборщик
ответов по шаблонам с исправленными багами и режимом рекомендаций; отправка
ответов через API с идемпотентностью и режимом «только черновики»; admin API справочников; интерфейсы
ключей и каталога; утилита переноса отзывов из старой базы (§10.7).

Приёмка: сквозной тест на поддельных серверах WB и Ozon — отзыв → ответ по шаблону отправлен ровно один
раз, повторный прогон ничего не шлёт; в режиме черновиков не отправляется ничего; пустой набор блоков не
роняет продавца. Перенос отзывов проверен интеграционным тестом на двух временных базах (источник — таблицы старого формата): пробный прогон ничего не пишет; `-apply` переносит всё; повторный `-apply` добавляет 0 строк; перенос не создаёт ни одного решения, черновика или задания.

### Этап 2. ИИ-решение и ручная очередь

Провайдеры ИИ; классификатор; политика; оба текста для очереди; ИИ-генерация ответа; короткие названия;
API ручной очереди; команда офлайн-оценки.

Приёмка: тесты на поддельном провайдере — все ветки политики; обрезанный и мусорный ответ модели не
приводит к действию; любой флаг риска уводит отзыв в ручную очередь при любой уверенности модели; ручные правки названий не перезаписываются; названия длиннее 7 слов
отбрасываются; офлайн-оценка работает на примере.

### Этап 3. Браузерный агент и жалобы

Серверная очередь заданий с арендой; протокол и регистрация устройств; агент под Windows (CDP, профили,
проверка авторизации и кабинета, запросы изнутри страницы, лимиты на endpoint, перезапуск браузера при
403/498, остановка при аномалии); адаптер кабинета WB (жалобы и статусы — по запросам из
`legacy/.../cabinet.py`); адаптер-заглушка Ozon (жалобы и ответы); маршрутизация оснований; проверка
текста; метка «жалоба отклонена» и возврат на ответ.

Приёмка: тесты на поддельном кабинете — локальном сервере с нужными адресами, страница которого открыта
в настоящем headless Chromium (поставить в среде), а агент шлёт запросы изнутри неё, — повторная жалоба
невозможна ни по нашей истории, ни по данным API; несовпадение кабинета прерывает действия; ответ 403 или
498 приводит к перезапуску браузера и продолжению **с того же задания** без его повторной отправки;
превышение лимита перезапусков останавливает кабинет; лимит запросов на endpoint соблюдается; отзыв с
меткой «жалоба отклонена» не уходит в авто-жалобу; задание с неизвестным исходом уходит в ручную очередь,
а не повторяется; бинарь собирается под Windows.

Реальные запросы WB и Ozon снимаются пробником этапа 0 на живых кабинетах; если записи уже есть в
`fixtures/probe/` на момент этапа 3 — адаптеры писать по ним, иначе WB — по запросам legacy, Ozon — заглушкой.

## 12. Чего в облачной среде нет и быть не должно

Живых ключей WB, Ozon, ИИ-провайдеров, доступа к кабинетам и к нашим серверам и базам. Все внешние вызовы
в тестах — через поддельные серверы и провайдеры. Проверка на реальных данных — после слияния, у нас.

Старая система жалоб **продолжает работать**. Новая не должна подавать жалобы на тех же продавцов, пока
старая не остановлена, — поэтому режим «только черновики» по умолчанию обязателен.
